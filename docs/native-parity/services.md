# Native AI and synchronization parity

Reference sources: `src/main/ai.cjs`, `ai-providers.cjs`, `ai-credentials.cjs`, `codex.cjs`, `claude.cjs`, `pdf.cjs`, `src/core/sync/model.cjs`, `src/main/sync/{client,controller,storage,vault}.cjs`, and `src/renderer/sync.js`. The services are native Swift actors; the app model and forms are SwiftUI/AppKit. Website document extraction remains engine-side page access, not browser UI implemented in JavaScript.

## Implemented AI service

- Six provider identities: ChatGPT/Codex subscription, Claude Code subscription, OpenAI API, Anthropic API, OpenAI-compatible API, OpenRouter.
- Profile/endpoint/provider-scoped API credentials use Keychain or explicitly chosen process-memory storage. Failed protected storage never silently writes plaintext. Corrupt preference files are preserved.
- Native Codex executable bundled without its Node launcher; Claude CLI discovered separately with a direct installation link. Owned processes receive a constrained environment and separate provider home, bounded output/time, cancellation, and cleanup.
- Subscription login/cancel/disconnect, available model selection, API connection checks without inference, endpoint validation, and explicit errors.
- Research, exact-address page grants, comparison, drafts, incremental Codex answers, cancellation, bounded conversation turns/context, citations and verified source actions. API transports return completed responses; they do not claim token streaming.
- Up to six reviewed pages, 20,000 characters per page, 60,000 total, 8,000-character questions, 120-second answer timeout. Navigation/profile changes invalidate context and old answers. Private profiles cannot read credentials, send questions, or reopen old source lists.
- PDF text extraction runs in `ZacroTextExtractor` using PDFKit in a disposable child process: 20MB input, 100 pages, 60,000 characters, 20 seconds, monitored 192MB resident memory. Citations preserve physical PDF page numbers; HTML quotes use text fragments.
- Download filename suggestions share metadata only and sanitize output while retaining the original extension.

`NativeServicesModel` filters profile-bound events, masks account state in private profiles, revalidates sync recovery export after the save dialog, and avoids context republishing on unchanged layouts. Completed profile tasks do not accumulate. Provider changes cancel pending sign-in only after the new settings are saved; failed saves preserve the old connection. Failed Codex startup clears pending login state so it can be retried. Page context grants are revalidated after asynchronous conversation reset.

## Implemented synchronization service

`NativeSyncClient` ports account registration/login/refresh/logout, device management, endpoint configuration, dataset/profile linking, separate library/settings opt-ins, merge/local choices, offline durable outbox, retry/backoff, idempotent acknowledgement recovery, rejection recovery export/retry/discard, account/profile invalidation, and explicit local profile deletion. Tokens are scoped to endpoint/account/device in Keychain.

`SyncModel` implements extension generation/revision identity, verified Web Store source filtering, last-write application and clear conflict semantics, detached local settings, storage access levels, get/getKeys/getBytesInUse/set/remove/clear, depth/size/item/write-rate quotas, and old/new-value events. Storage changes are published after durable persistence.

## Native engine integration

`NativeExtensionSync` connects the service to the Chromium manager without injecting a storage shim into extension JavaScript. Startup initializes only the active public profile and linked profiles; explicit review and native events initialize other profiles on demand.

- Verified `FROM_STORE` registry records become minimal portable descriptors. Unpacked, policy-forced, invalid and unknown sources remain local. Native install/enable/remove observations create library changes. Missing remote installations remain visible as **Review & install** and use Chromium's Web Store permission prompt.
- Per-profile operation queues, current account/link/generation checks, and native installation nonces prevent old asynchronous events from applying to replacement installations. Failed native reads throw through the library review rather than pretending the local library is empty. Apply failures remain visible with an explicit retry.
- Native `StorageFrontend` observations carry trusted local/private/remote provenance. Local accepted changes use `observeNativeStorageChanges` once; they are not replayed as JavaScript calls or charged a second write quota. `seedNativeStorage` initializes a local mirror for a reviewed upload choice, and cannot replace an already linked cloud view. Unchanged or already linked seeds do not rewrite the service file, so a no-op observation cannot fail merely because disk storage becomes unwritable.
- A full `nativeStorageProjections` snapshot supports restart, settings sync with library sync paused, and recovery after missed events. Exact current values plus link/generation guards invalidate stale applies. The manager passes a native installation nonce and exact prior dictionary to remote apply.
- A bounded native baseline and two-phase remote marker share the durable service transaction. Intent is saved before native apply, and acknowledgement after. Restart recovers unmirrored native local changes into the outbox; exact before/target dictionaries identify an interrupted remote commit without echo. Ambiguous overlaps and differing legacy states require an explicit **Keep local settings** or **Use synced settings** choice. A failed marker write prevents native apply, and profile deletion removes its recovery data. Chromium's first-install identity binds recovery records across restarts: updates preserve it, and a reinstall retires its old baseline without publishing its defaults as deletions. Production native snapshots require a valid same-extension first-install identity; missing or malformed metadata blocks cloud settings operations with a retry message while local extension use remains available. Native install/uninstall events are serialized with storage events; failed durable cleanup blocks reconciliation until retry.
- The pinned Chromium adapter implements compare-and-replace on the storage backend sequence: final dictionary quota validation, one LevelDB WriteBatch, and one native/JavaScript change event. Private origins and `zacro.remote:` writes cannot echo back to the cloud. Unsupported storage implementations fail closed; there is no sequential Set/Remove approximation.

The current engine maps private browsing to independent ephemeral profiles. Sharing Chromium's original and off-the-record extension storage in a future mapping would require an additional durable exclusion baseline; an origin tag alone would not stop a later full snapshot from containing private-origin changes.

The source adapters and coordinator are implemented, but the custom Chromium framework and its native extension fixtures must still compile and pass. End-to-end Chrome storage synchronization and universal Chrome extension compatibility remain unverified until that acceptance finishes.

## Opaque navigation state

`NativeNavigationStateStore` stores the engine's already encrypted history envelope outside the bounded browser-state JSON. It never decrypts PageState or uses Keychain itself. Records are scoped by hashed profile/tab IDs and main/Peek slot, bind the current address, and cap payloads at 6MiB. Reads reject private/missing profiles, symlinks, oversized or corrupt metadata, wrong URLs and payload digest mismatches. Directories use 0700 permissions and atomic files use 0600.

The vault supports restart, copy, Peek promotion, per-slot removal and whole-profile removal. Pending captures cannot recreate a slot after deletion: profile and slot revisions are checked across the asynchronous profile lookup. Stale reads cannot delete a newer capture. Root navigation integration must still explicitly invalidate same-URL resets/imports; URL binding alone cannot identify those transitions.

## Shutdown and profile deletion

The application owns one AI actor and one sync actor. `NativeServicesModel(store:sharing:)` creates per-window presentation models that subscribe to those actors while retaining their own context grants and conversation UI. Read-only scoped status APIs display the correct profile in background windows. Actions supply the expected profile to the shared actor so a focus race fails before another profile is configured. Only the backend starts sync, handles library/storage events and performs deletion recovery; closing a window cancels its subscriptions without stopping the shared services. Reopening a retained window can start its subscriptions again. Extension observation initializes active public profiles from every open native window, plus linked sync profiles.

The full 2026-11-02 run passed 98 Core and 64 Services tests with zero failures or skips, including the bundled Codex handshake and PDF helper (`macos/.build/verification/core-services-post11.log`). Two added service cases verify background status isolation and rejection of stale-window mutations. The scoped presentation model was separately typechecked against the actual Core/Services modules; integrated AppKit acceptance remains required.

`NativeServicesModel.shutdown()` (also exposed through `close()`) is an idempotent asynchronous barrier. Invoke it after beforeunload consent and before engine destruction. AI and sync close concurrently; owned provider processes receive termination, escalate to SIGKILL after one second, and are reaped. A child-process test verifies shutdown completes before a 30-second child’s ordinary exit.

Profile deletion has two phases: `prepareProfileDeletion` durably blocks sync and cancels AI while retaining local data; after `BrowserStore.deleteProfileDurably` succeeds, retire the engine profile and call `didDeleteProfile` to remove service data. If the store transaction fails, `cancelProfileDeletion` restores availability without losing extension settings. Startup reconciles an interrupted prepare against the authoritative browser profile list. Cleanup failure remains visible and can be retried.

CI installs only pinned production dependencies without package scripts to obtain the native Codex binary, explicitly builds the PDF helper before service tests, and reruns the PDF tests against the bundled helper and the unauthenticated Codex handshake against the bundled native provider. The bundler rejects a Codex executable that does not report the pinned 0.164.0 version.

The bundle metadata step preserves generated CEF keys and applies the original application's `http`/`https` URL registration before signing. It corrects the old manifest's `CFBundleURLRole` typo to Apple's required [`CFBundleTypeRole`](https://developer.apple.com/documentation/bundleresources/information-property-list/cfbundleurltypes/cfbundletyperole). Camera, microphone, and location descriptions match the implemented native permission delegates. The native deployment minimum is macOS 14, matching `Package.swift`. The source browser has no file/document association declarations, and the native open handler accepts only web URLs, so this bundle does not advertise unsupported file handlers. Metadata updates are idempotent; a temporary-plist check verified schemes, descriptions, minimum OS, and preservation of generated keys.

Live process checks on 2026-11-01: the packaged Codex 0.164.0 completed initialize, tool/skill inventory, and account/read with `available=true`, `configured=false`, session storage, and no model calls. The asynchronous RPC writer also passed a deliberately blocked stdin probe (512KB sent to a non-reading child): shutdown completed in 0.082 seconds, rejected the request, and did not crash from SIGPIPE. Provider pipe descriptors disable SIGPIPE individually; writes run on a serial background queue so provider backpressure cannot block the actor responsible for cancellation.
