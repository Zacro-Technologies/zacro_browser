# Native history reconciliation

The Swift Library and Chromium's HistoryService have different responsibilities. The Library retains at most 20,000 visits and follows the Electron app's full-document commit policy. Chromium owns actual VisitIDs, navigation history, extension history APIs and deletion. A private journal in that same native History database connects those stores without matching visits by address or nearest timestamp.

## Native authority

The browser process preregisters each public logical document before its first navigation. Each eligible actual native visit carries a WebContents-owned document token, a new navigation event UUID and a process epoch. The final post-redirect native VisitID and the handoff row share Chromium's existing SQL transaction. The checked flush reports COMMIT failure rather than publishing successful-looking data. Genuine `chrome.history.addUrl` visits also receive native-owned identities; the existing extension permission and validation paths remain in effect.

Same-document SPA navigation retains its document token and receives a new actual native event identity. Its `libraryVisit=false` flag preserves the Electron behavior: pushState, replaceState and same-document back/forward do not append extra Library rows. Intermediate SPA handoffs are superseded within that exact document, without deleting native visits. Explicit full-sizing of a Peek can publish its captured current SPA event.

Database identity is a private random UUID plus a monotonically advancing reset counter. The reset marker and visit-table recreation share the actual native transaction. Only a successfully committed later counter of that same database proves an old epoch absent. An unrelated, malformed, interrupted or unreadable database remains unavailable. Numeric VisitID reuse cannot revive an old event because generation and native microsecond visit time are checked as well.

## Durable reconciliation

Native observation requests a drain; it is not deletion proof. The profile-owned native observer issues bounded revision leases. Every verification page must preserve its lease, revision, offset and exact input identities, and a DB-queue confirmation must still match before Core removes anything. A complete Core deletion plus its acknowledgement receipt is one durable write, with recovery copies purged. A lost response can replay the exact receipt safely.

A binding captures the Core row UUID, profile, address and visit time as well as the exact native identity. Deletion removes only that unchanged bound version. A newer coalesced visit, another profile, tabs, archived tabs, Peek state and live back/forward stacks are unaffected. Optional late title metadata comes from the exact current native event and live weak document; historical URL-table titles are not used to overwrite every old same-URL Library row.

Native events are paged by a decimal sequence. Core appends a Library visit and writes its opaque event receipt atomically, then acknowledges the native journal and removes the Core receipt. Replay after a lost acknowledgement does not append another visit. A native tombstone can remove only its exact previously committed version. Unpublished Peek tombstones remain native until promotion, cancellation or exact producer closure; they are not prematurely consumed as public Library history.

## Initial and explicit legacy import

Pre-native Library rows are deliberately imported as real historical native visits. Each import identity hashes a versioned, length-prefixed tuple of profile, Core row UUID, exact source address and source visit-time bits. Title metadata is excluded. A changed title retries the same native visit; a real newer coalesced visit has a new identity. Portable history import authors fresh Core row UUIDs, so intentional reimport is a new action.

Before inserting any batch, Core durably assigns its entire captured unbound snapshot to an opaque native deletion boundary. The native database records subsequent explicit URL/range deletion scopes as canonical URL hashes and exact native time ranges, including deletion requests that currently match no native URL. An unsubmitted legacy row covered by that later deletion becomes an idempotent native tombstone rather than being reinserted. Delete-all/reset also invalidates prior native generations. The initial baseline remains until Core confirms the entire initial migration; discarded or lost prepare responses cannot skip an intervening clear. Later intentional imports receive a current boundary.

Native import owns an independent SQL transaction after preserving unrelated browsing. Its actual historical visit and opaque import journal commit together, without generating a fresh navigation event that could duplicate the Library row. Core accepts only the exact unchanged unbound row, the attested boundary and the requested microsecond time. Chromium's genuine GURL spelling remains the native identity; a source-address hash attestation handles Foundation/GURL canonicalization differences without guessing URL equivalence. Native acknowledgement and Core recovery-copy cleanup finish the handoff. Metadata contains no additional durable URL/title copies.

## Retention and lifecycle

Chromium's automatic age expiry must not erase Library rows that the Electron app retained by count. Exact Core-retained VisitID/generation/time tuples and pending published/import journals are excluded from automatic expiry before its SQL LIMIT, preventing starvation behind protected old rows. The full retention snapshot is replaced atomically in a dedicated transaction. Explicit user and extension deletion bypasses this retention. A read-only status exposes the automatic reader count and retained tuple count for the actual old-visit acceptance check; there is no test mutation endpoint.

Popup adoption and Peek promotion require a native-prepared publication boundary. Preparation also captures the application profile epoch. The factory revalidates it after native preparation, and adoption/promotion synchronously validates it immediately before the atomic Core commit. A clear/reset/profile removal invalidates that epoch even after its visible operation flag disappears; an authorization await cannot publish a stale captured visit after a completed clear. The new Core tab/promotion and opaque publication receipt commit together. Only that surviving receipt can publish native events. The receipt remains valid after a tab closes, but cannot reopen it. Native registration, publication acknowledgement and finalization tolerate lost responses. Orphan cleanup uses an exact producer destruction notification or a prior process epoch, never an earlier snapshot that happened not to contain a newly created producer.

Public-profile history clear suspends the application drain and waits an ordering-only native DB barrier before deletion. BrowsingDataRemover completion is followed by checked native SQL observation before Core clears; profile-wide data clear borrows its retained live maintenance page instead of recreating a closed broker. Cancelling a Swift task alone cannot retract an already-submitted native import. Profile deletion pauses the extension/native event observer before closing its hidden broker. A veto or setup failure explicitly resumes observation after releasing the profile operation lock, so it does not deliberately retain an old DevTools registration. Actual veto/reconnect acceptance remains pending. Profile retirement cancels its observer, pending native replies and verification leases. Shutdown closes existing lanes/transports without creating a replacement browser context. Unknown/transient runtime capability failure blocks preparation or clear and can retry; only an explicit unsupported-method result selects stock-runtime fallback.
