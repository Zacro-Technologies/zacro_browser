# Browser security and maintenance

## Trust boundaries

The main process owns operating-system capabilities. The local application renderer receives a narrow IPC action bridge; every invocation must come from that renderer's main frame. Visited websites must never receive this bridge. Remote content uses sandboxed, context-isolated WebContentsViews with Node disabled and normal web security enabled. User-entered navigation accepts HTTP and HTTPS only; internal new-tab pages are rendered by the shell. Authenticated extension APIs can also open their own enabled extension pages through a separate host-only route. The shell cannot invoke that route or navigate to broker resources. File, JavaScript and arbitrary external-protocol navigation is rejected. TLS errors are not bypassed.

Each profile has its own Chromium session partition. Private profiles use non-persistent partitions. Browser state filters private records before disk writes and portable exports. Downloads explicitly saved by users remain on disk even when initiated privately. Private browsing does not hide traffic from sites, network operators or the operating system.

Packaged Windows and macOS builds disable Electron's RunAsNode, NODE_OPTIONS and main-process CLI inspection fuses, enable OS cookie encryption and embedded ASAR integrity validation, and load application code only from ASAR. Development Electron binaries used by the test harness retain their normal debugging capabilities. macOS publisher releases additionally use Hardened Runtime, Developer ID signing, notarization and ticket validation. Ad-hoc development builds explicitly disable Hardened Runtime and do not establish publisher trust; they are named as development artifacts. The build checks the native Electron and Codex executable architectures before packaging. HTTP/proxy authentication uses an expiring, single-use request tied to the requesting page and profile; credentials go directly to Chromium's authentication callback and never into browsing-state records.

macOS web-address delivery is queued before startup and while reopening a closed window. It accepts the same bounded HTTP/HTTPS URLs as browser navigation, rejecting credentials, executable/file schemes and malformed input. Declaring web-address support in the application bundle does not silently change the user's default browser. macOS privacy purpose strings describe camera, microphone and location use; they do not grant a website or Zacro permission by themselves. Chromium site decisions and macOS consent remain separate boundaries.

Site permission decisions are scoped by profile and requesting origin; requests that cannot establish a trustworthy origin must be denied. Unpacked extensions are privileged third-party code: install only after reviewing their identity and requested permissions, do not load them into private profiles, and do not promise Chromium APIs the runtime does not implement.

AI is opt-in through an explicitly selected subscription or API connection. Zacro's bundled Codex app-server and supported Claude Code connection use isolated configurations without importing another installation's credentials. Codex uses the OS keyring; a storage failure requires an explicit session-only choice rather than a plaintext fallback. Claude Code manages its own storage, including local credential files on Windows/Linux and a possible file fallback on macOS; that policy is disclosed before sign-in. API keys are scoped to a browser profile, provider and exact endpoint, and use available OS encryption or explicit session-only storage. Tokens and saved keys never enter renderer snapshots, portable exports or sync records. Inherited API keys and custom provider endpoints are excluded from subscription child processes. There is no automatic provider or API billing fallback. See [connection-specific enforcement and live-account limits](AI.md).

Website login popups preserve the native Chromium opener and session. Favorites with a live popup are protected from sleeping so callback listeners survive; popup closure restores the opener only when the popup was active. Identity providers may still reject an embedded browser. See [website sign-in and Google's support boundary](WEB-SIGN-IN.md).

Codex requests use ephemeral threads, read-only sandboxing, never-approve policy, and explicit empty execution-environment lists at both thread and turn start. Local tools, plugins and skills are disabled; MCP discovery or policy failures stop the connection. Unexpected tools and approval requests fail closed. Hosted web search is limited to research; page/PDF context and filename suggestions disable it. Page text and web results are untrusted evidence, not authority to execute instructions. This version cannot submit purchases, messages or forms on behalf of a model. See [AI boundaries](AI.md) for the version-specific enforcement and verification limits.

PDF context is parsed locally in a disposable worker with input, page, text, time and JavaScript-heap limits. Only static text is shared after explicit selection. No raw PDF file, form annotations, or PDF JavaScript is sent to or executed for the provider.

Site icons are optional presentation data. Saved pins, Favorites, and Peek destinations retain validated icons in separate local raster files, scoped to their profile and saved URL. Each file is at most 128 KiB; the saved-tab limit bounds the number of files. A 128-entry / 4 MiB memory cache speeds up reads without evicting saved files. Private icons stay in memory. Clearing browsing data or deleting a profile removes its saved icons; tab exports never include them. The host retrieves only same-origin raster candidates using the originating Chromium session, refuses redirects, and bounds requests to 128 KiB and four concurrent fetches. PNG dimensions and simple ICO structures are validated before image bytes reach the sandboxed shell. The shell never loads a website's favicon URL directly. SVG and unsupported or cross-origin icons fall back to a monogram; caches cannot cross session partitions.

When a command dialog covers a web page, the shell may receive a temporary local screenshot to preserve the visual background. Captures are bounded, never written to disk or sent to an AI provider, disabled in private profiles, and cleared when the dialog closes or its page/profile changes. Late capture responses must not restore an old profile's image. This is visual presentation, not permission to extract or share page content.

## Extensions and account synchronization

Web Store acquisition accepts a canonical store ID, follows only bounded HTTPS distribution routes and verifies both the CRX3 developer identity and production publisher proof. Archive expansion checks paths, file types, duplicate/case collisions, CRCs, sizes and depth. Originals and manifests are retained; generated adapters have separate hashes and are not presented as the publisher's signed bytes. Unpacked folders are copied into managed storage and labeled local-only.

The compatibility bridge runs only in native extension contexts. Its hidden broker authenticates native extension identity, source document and lifecycle generation; a web page cannot choose its extension/profile namespace or access shell IPC. Content contexts additionally obey the extension's current storage access level. Background notifications recheck ownership and access before delivery. Disabling, removing or reducing permissions unloads native code and revokes adapter generations. Already injected page scripts can require reload; cancelled unsaved-page navigation keeps a reduction pending and the extension disabled.

Optional permissions are separate from declarations. Approved rights rebuild the effective native manifest; removing them cannot be simulated solely with a JavaScript facade. Engine capabilities that cannot be enforced remain unavailable. In particular, native `activeTab` is not replaced by broad host access. Representative compatibility and background lifecycle verification are tracked in [the feature record](EXTENSIONS-SYNC-VALIDATION.md).

Account tokens live in a separate main-process vault protected by Electron safeStorage. Unavailable credential protection fails closed, including Linux's `basic_text` backend. Routine snapshots and browser exports exclude passwords, tokens, recovery codes, settings values and extension paths. Recovery codes are shown only in explicit one-time account flows. Packaged clients require HTTPS; numeric-loopback HTTP is an explicit development-only option.

Profiles link to datasets explicitly; sign-in or matching names do not establish a link. Library synchronization carries portable Web Store IDs and desired state, with per-device permission review. Settings synchronization starts off and requires separate informed consent. Local storage and sync storage are distinct. The latter obeys quotas and event/access rules, with account-separated local archives, persistent offline operations and explicit rejected-change handling. Service/account/profile changes invalidate in-flight work. Private profiles cannot load extensions or use account controls.

The separate service authenticates each device/operation, stores bounded scrypt password hashes, rotates refresh tokens and revokes replayed sessions. Per-account keys encrypt sensitive data at rest under an external master key. The running service can decrypt extension settings: this is not end-to-end encryption. Extension-authored values may contain sensitive information even though the protocol does not copy Zacro cookies, site sessions, browser passwords or AI credentials. Cloud deletion and device revocation cannot erase copies already downloaded to another computer. See [service operations](../services/sync/README.md) for threat boundaries, backups and recovery; production deployment and independent security assessment remain release gates.

## Data recovery

Browser state is schema-validated on load, written to a flushed temporary file and renamed into place. The previous valid state is retained in `.bak`. Damaged input is preserved for recovery rather than silently destroyed. Explicit history, permission, archive and profile deletion also sanitizes the recovery copies, so a later recovery cannot resurrect cleared records. See [data recovery and deletion](DATA-RECOVERY.md) for the boundaries. Managed extensions use separate metadata and durable legacy-import receipts so an old browser backup cannot reinstall an extension removed after migration. Account/sync state is stored separately in SQLite and is excluded from portable browser exports. Cloud restoration requires the current durable security ledger; old backups cannot be restored safely with an old ledger.

Portable imports merge with fresh IDs; they cannot install extension paths, import credentials, grant permissions or replace current settings. Bookmark imports accept web URLs and text labels only.

## Maintenance policy before release

Pin Electron and development tooling in package-lock.json. Dependabot checks weekly, with security alerts reviewed daily by the designated release owner. Chromium/Electron critical fixes must trigger an emergency build and regression pass; the team must name an owner and response time before public release. Never retain a known-vulnerable runtime merely to preserve an extension behavior.

Check runtime advisories, run `npm audit`, review lockfile changes, run the full test suite, test the signed installer and stage updates before promotion. Installer signing, an update origin, signing-key custody and rollback procedures require operational provisioning; source code cannot supply these credentials.

For reports, use GitHub private vulnerability reporting if enabled for this repository. Do not post keys, personal browsing data or exploit details in public issues. Repository administrators must enable and staff a private reporting channel before a public release.
